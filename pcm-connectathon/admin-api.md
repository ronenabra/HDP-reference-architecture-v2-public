When `TEAM_ADMIN_PASSWORD` is set, send it as `x-admin-password` or a POST form/JSON `adminPassword` field; the browser can use its authenticated Admin cookie. The admin web UI uses the same protection.

Admin → Certificates presents a read-only owner/role inventory. Exact registry IDs
filter PCM, source, SP app and system-client facts. Backend certificate/key agreement
checks expose fixed outcomes only; neither file validity nor current client resolver
agreement proves that a running listener loaded a file. Listener adoption remains
unknown. Source HTTPS trust is separate from client transport/assertion registration;
remote server certificates stay unobserved until independently checked. Source
generation/upload remains in Sources; new SP onboarding is deferred.

`GET /admin/certs/download-bundle` and `/admin/certs/download-zip` are explicit
credential exports under the same Admin protection. Both include current directory
files, private keys and any present CA keys for permitted portability. JSON adds
public owner/role facts; ZIP retains the existing file layout. Responses use
`Cache-Control: no-store` and attachment disposition. They are not public fingerprint
exports or complete team backups: config, environment, databases, Consents and logs
are separate. Inventory pages, Help and status responses never include key contents.

`POST /admin/certs/regenerate` now returns HTTP 409 with
`code=certificate-recreation-required`, the registered leaf-role inventory and
controlled operator instructions. HTML renders this expected handoff in Certificates
without an action-failed banner; the 409 API boundary remains. It changes no credentials. Managed HAPI/NGINX
listeners cannot be safely recreated by the Admin process. Use the maintained
local `rotate-team-certificates.js` preview/apply workflow below; root authorities
and negative-test material stay unchanged.

```bash
node pcm-connectathon/scripts/rotate-team-certificates.js --team-id <team> --teams-root <teams-directory>
node pcm-connectathon/scripts/rotate-team-certificates.js --team-id <team> --teams-root <teams-directory> --apply
```

Add `--rotate-keys` for explicit private-key replacement; otherwise renewal keeps
keys (and signing JWK identities). Renewed certificate fingerprints can invalidate
old correlated tokens even without key replacement; obtain fresh credentials/tokens
and restart affected tests. Source/app IDs and authority deadlines stay fixed.
Apply stages/validates the complete selection,
backs up files privately, stops only that Compose project, publishes matching
config/credentials and recreates listeners without removing volumes. It is an
interruption, not zero-downtime rotation. Failure after successful cleanup restores
the previous graph and leaves the team stopped. A failed stop/restore reports
uncertain state and retains recoverable material; do not start listeners until
reconciled. The backup path is printed only after an accepted operation.

Custom credentials generated by current Admin tooling carry server-owned
`pcmClientAuth.managedBy=team`; uploads carry `participant`. Older unknown custom
ownership is preserved, not inferred from a trusted chain. Resolve an unknown
alias to a selected team file before renewal. Source-specific explicit Generate
can adopt that source's material under team control. Independent source HTTPS
CA/pins are preserved except an explicitly tied pin moves with its renewed leaf.


Both `GET /admin/logs` and `GET /admin/logs/download` return the existing `logs`
map plus `status`, `complete` and `failures`. A complete configured-source read
returns HTTP 200, `status: "complete"`, `complete: true`, and an empty failures
array. A rejected/unreadable source returns HTTP 207, `status: "partial"`,
`complete: false`, healthy source logs and failures containing component IDs and
errors. Failed sources are omitted, never represented as empty successful
streams. Check completeness before using the result as a full export.

Preparation uses asynchronous, private temporary staging before a backpressure-aware
transfer. Clear during preparation returns HTTP 409 with an error and no export;
retry against a fresh snapshot. Staging failures return HTTP 500, never a partial
source success. An already-prepared transfer is not revoked by a later clear.
The existing client timeout is unchanged and no arbitrary-volume first-byte SLA
is promised. See [the full export contract](../docs/public-quickstart.md).

The automated E2E sanity flow is provided by `pcm-connectathon/scripts/run-sanity-check.js` and can also be run through `POST /admin/sanity-check` from the admin UI. Browser submissions render the Admin page again with an inline OK/error summary and expandable JSON details; API clients can request JSON.

Managed clinical-data operations target configured HAPI servers only; the
legacy Node compatibility Data Source is deliberately excluded. Imports accept
a bounded `*.source.transaction.json` multipart upload, check its R4 transaction
shape, references, synthetic tags, allowed types, limits, checksum and counts
before mutation, and return `202` with a persistent operation ID. These are
bundle contract checks; full FHIR profile validation is not performed. HAPI's
transaction response is checked separately from read-only, source-tagged
post-load per-type verification. Only verified inventory is published. Reset
requires the exact target confirmation token returned by the inventory API. Poll the
operation endpoint for queued, validating, resetting, loading, verifying,
succeeded or failed state and complete diagnostics. Each operation records
`currentStage`, `stageStartedAt`, `stageTimestamps`, `progressEvents`,
`lastCompletedStage`, and verified type counts when known. The status GET also
returns server `observedAt`, current `elapsedMilliseconds`,
`stageElapsedMilliseconds`, `waitMilliseconds` and the latest
`transactionDeadlineAt` from transaction submission plus the configured
connect/upload and response wait budgets. The actual HAPI response wait starts
after upload, so this timestamp is an upper bound. A pending atomic transaction
has no resource-level percentage. After a missed deadline or lost polling,
clients must treat the saved stage as last observed state until the server
records a terminal result. The protected `GET /admin/api/patients` returns
identifiers from verified import records for Admin; it does not establish live
source presence. The anonymous bridge has been removed. Controlled test setup
uses [named private fixture checks](fixture-qualification.md); Doctor has no
maintenance credential.

`POST /admin/config/simulation` accepts exactly the four documented presets,
all versioned global controls and per-source overrides. AWS credential
isolation is returned as an always-on invariant and cannot be disabled.
Connectathon logs and downloads preserve full non-AWS credentials and synthetic
Patient/FHIR values, so treat them as sensitive local artifacts. AWS
operational credential values are always prohibited.

Admin and CLI share one per-target operation ledger and clinical workflow.
Ownership starts before the authoritative empty/history probe; `if-empty` skips
preserve the verified inventory. Container cleanup precedes CLI publication;
saved uploads remain until verified ledger publication and are then removed.
Uncertain submitted mutations and verification/publication failures retain
ownership and hide unverified inventory. A verified upload cleanup failure is
recorded and leaves a residual file. A conflict returns HTTP 409
with the active operation ID. Recovery requires confirmation that the worker
and HAPI transaction stopped. A submitted POST is checked against the saved
upload, target identity, full live resource bodies, references and history;
only complete proof publishes inventory. Incomplete evidence retains the target
lock for reviewed scoped reset/replacement. `POST /admin/api/data-operations/{operationId}/reset`
requires the exact target confirmation and verifies zero resource/history state
before releasing the old reservation. Recovery never replays a POST.
Effective stage deadlines, failure stage and unknown submitted outcome appear
in the operation record. Existing complete
legacy markers are reconciled against target, checksum and full live content,
references, counts and history
before conversion to ledger inventory and retirement. See
[clinical lifecycle](../clinical-data/README.md).

Explicit `LOCAL_JWT_KEY_ID` overrides require private adapter/native configuration review before key replacement; the command refuses them before stopping listeners. Same-key leaf renewal remains available.

### Source institution classification

The existing source registry stores `institutionType`: `hmo`, `hospital` or
`other`. Admin's source cards save it through
`POST /admin/config/data-sources/:id/institution`, using the stable source
Organization ID, `institutionType` and `expectedRevision` from the current config.
The same Admin authentication applies. Invalid types return 400, unknown sources
404 and stale revisions 409; refresh and review before retrying. Successful saves
advance the existing runtime revision and record an Admin audit event. Disabled
custom sources retain an editable classification without being enabled.

Custom creation accepts the same field and defaults to Other. Known managed
`ho-a`/`ho-b`/`ho-c` entries default to HMO when an older config omits it; unclassified
custom/legacy sources default to Other. Explicit types survive credential/trust
changes and backup/restore because they belong to the source record. The fixed
three-managed-HO topology remains unchanged; a custom HMO stays custom.

Classification alone does not prove HMO membership or patient data, authenticate
anyone, grant clinical Consent, or remove Hospital sources from clinical choices.
PCM test authentication and dependent discovery now resolve registered HMO sources through their current Organization, Endpoint, Contract and source-trust prerequisites.

### HMO test workflow source policies

Ordinary supported national-ID tests choose a source Organization ID classified
HMO; they do not need `memberships` or `participatingHmos`. Those old fields no
longer govern participation. Explicit SSO/HTEST fixtures and foreign-passport
eligibility facts retain their own requirements. A chosen source is a declared
local test target, not verified real-world membership. Matching Patient/DOB,
marked fresh OTP contact and successful browser-bound local code checks remain
required. Presence eligibility/EULA and clinical Consent remain independent.

Authenticated source configuration publication stages new registrations and
validates authentication/discovery Contract source assets in the existing FHIR
transaction before publishing configuration. Live source additions/reclassification/
removal update those explicit assets without changing Contract identity, issued,
start or end. A private 0600 backup under `state/workflow-source-backups` precedes
policy maintenance. Invalid, expired or terminal policies requiring source changes
refuse publication with an actionable error; no automatic revival/replacement or
validity extension occurs. Existing Organization/Endpoint lifecycle state is
preserved. Removed/reclassified sources and changed endpoint/trust state invalidate
workflow authority, including late results; ordinary positive caches keep their
existing 30-second ceiling. New registrations never widen an issued token.

For an existing installation, first review the registered source classifications
and back up its current configuration using the protected Admin backup path.
Preview the current source/Contract graph with:

```sh
node pcm-connectathon/scripts/reconcile-hmo-workflows.js --config TEAM/team-config.json --team-env TEAM/.env --output /private/hmo-review.json
node pcm-connectathon/scripts/reconcile-hmo-workflows.js --config TEAM/team-config.json --team-env TEAM/.env --apply --review /private/hmo-review.json
```

The CLI uses the configured protected UI listener and keeps its Admin credential
in the local process. The reviewed config revision, exact Contract versions and
source set must still match. The corresponding private endpoints are
`GET /admin/workflow-sources/preview` and `POST /admin/workflow-sources/apply`.
Preview reports each policy's current lifecycle/readiness even when its source graph is unchanged; missing policies block apply. A no-op graph performs no policy replacement. A changed valid graph is backed up
before maintenance; terminal/expired grants require an explicitly reviewed new
Contract through existing policy lifecycle tooling. Do not reset PCM or reload
clinical data to force acceptance. No retained installation was migrated as part
of development.

Source CA uploads use content-specific certificate paths, preserving previous files
for backup/recovery and invalidating flows bound to changed trust.

Custom HMOs use their current authoritative registered Endpoint and existing configured HTTPS trust
mode. PCM sends its own registered workflow client's transport/assertion roles,
with actual certificate `cnf`; it never borrows the source's OAuth identity or
maintenance credential. Unsupported FHIR, bad trust, missing credentials and
partial discovery remain explicit failures/unknown source outcomes.
